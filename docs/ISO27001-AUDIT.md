## HIGH (3)

### HIGH-1 · A.8.3 Information access restriction · `app`

**Cloud Storage delete is granted to any org member, so the read-only auditor can destroy every uploaded file in the tenant**

**Gap.** The two enforcement surfaces disagree. In Firestore a member cannot delete and an auditor cannot write at all; in Storage both can delete anything in the org. The files are the evidence — incident photos, permit documents, LOTO procedure photos, drill evidence — and the auditor is described in the code itself (firestore.rules:56-61) as an outside party given a login to inspect the safety record. Deletion is unrecoverable and leaves no trace in the append-only audit log, which only records app-initiated actions.

**Fix.** Read the role claim in storage.rules the same way orgId is read: add `function canWrite(orgId) { return inOrg(orgId) && request.auth.token.get('role','') != 'auditor' }` and gate `delete` on manager/admin to mirror firestore.rules:791 — `request.auth.token.get('role','') in ['admin','manager']`. Extend tests/storage.rules.test.js with auditor and manager token contexts so the role dimension is covered.

<details><summary>Evidence</summary>

storage.rules:47-49 defines the only gate, `inOrg(orgId) = request.auth.token.get('orgId','') == orgId` — organization membership and nothing else. storage.rules:68 `allow delete: if inOrg(orgId);` and storage.rules:52 `allow read: if inOrg(orgId);`. The role IS available on the token: functions/lib/claims.js:24 `CLAIM_KEYS = ['orgId','role']` and claims.js:38 returns `{orgId, role}` for an approved member, and syncUserClaims stamps it (functions/index.js:85). storage.rules never reads it. Firestore, by contrast, excludes the auditor from every write (firestore.rules:62-64 `isWriterOf` = approved && role != 'auditor') and requires a manager to delete (firestore.rules:791 `allow delete: if ... isManagerOf(orgId)`). tests/storage.rules.test.js:49-50 mints only `role:'member'` tokens, which is why the role dimension was never exercised.
</details>

### HIGH-2 · A.8.22 Segregation of networks (tenant segregation) · `app`

**Any tenant can squat an unindexed org name in /orgIndex and capture every future joiner of that org**

**Gap.** The create rule proves the writer owns the orgId in the payload but never proves the writer owns the NAME being claimed. Registering an org is self-service, so that precondition costs one signup. Every pre-index org (the reason ensureOrgIndex exists) is a live target, and the capture is permanent.

**Fix.** Bind the key to the payload and to the org's own record: add `getAfter(/databases/$(database)/documents/organizations/$(request.resource.data.orgId)).data.nameLower == key` to the create condition (createOrganization already writes nameLower, src/shared/org/orgData.js:85). Add the missing test — an attacker who DOES hold an approved profile in their own org — beside tests/firestore.rules.test.js:249. Then sweep production /orgIndex for entries whose key does not equal the target org's nameLower.

<details><summary>Evidence</summary>

firestore.rules:298-310 — `allow create` requires only `getAfter(users/$(uid)).data.orgId == request.resource.data.orgId`. Nothing binds the document ID (the lowercased org NAME, per src/shared/org/orgData.js:44-45) to the org the payload points at, so any signed-in user who is an approved member of ANY org may create an index entry under ANY name not yet taken, pointing at their own org. Signup consumes exactly this: src/pages/auth/Signup.jsx:18-22 populates the org dropdown from listOrganizations() (src/shared/org/orgData.js:113-120) and src/shared/auth/AuthContext.jsx:131-143 enrols the joiner against the orgId that entry carries. The victim can never repair it — ensureOrgIndex() returns early when the doc exists (src/modules/fire/lib/firestore.js:162-172, same in ptw/incidents/committee), and the update rule (firestore.rules:306-308) is pinned to the SQUATTER's orgId. Confirmed on the emulator against the live rules file: bob (approved admin of orgB) created orgIndex/'acme corp' = {orgId:'orgB'} successfully; alice (admin of orgA) was then denied on both create (L300) and update (L306). docs/SECURITY.md:269-273 records this class as fixed (S-18, 'orgIndex tenant hijack at signup'), and tests/firestore.rules.test.js:249-255 asserts only the profile-less stranger case — a caller with no /users doc, which the getAfter pin does stop. The caller WITH a throwaway org is untested and allowed.
</details>

### HIGH-3 · A.8.22 Segregation of networks (tenant segregation) · `app`

**/procedureQr entries for another tenant's LOTO procedures can be claimed on create, and the owner can then never publish or delete its own isolation page**

**Gap.** A public collection whose IDs are derived from one tenant's data accepts creates from every tenant. The result is attacker-controlled isolation instructions served at the URL printed on someone else's machine, plus permanent denial of the owner's backfill — on the LOTO surface, which is the one a worker reads before putting hands inside equipment.

**Fix.** Bind the mirror ID to the procedure it mirrors: `allow create: if isWriterOf(request.resource.data.orgId) && get(/databases/$(database)/documents/procedures/$(procedureId)).data.orgId == request.resource.data.orgId`. Run backfillProcedureMirrors (src/modules/loto/services/procedures.js:585) for every tenant afterwards, and audit existing /procedureQr documents for any whose orgId disagrees with /procedures/{id}.orgId.

<details><summary>Evidence</summary>

firestore.rules:381-389 — `allow create: if isWriterOf(request.resource.data.orgId)`. Unlike /qr and /permitQr, whose document IDs are 18 random characters minted at print time (src/modules/fire/lib/qr.js:7-11, src/modules/ptw/lib/qr.js:6-10), this collection is keyed by the PROCEDURE ID (firestore.rules:376-378; src/modules/loto/utils/publicProcedure.js:23-25), which is printed in the scannable URL /p/<id>. Any writer in any tenant may therefore create the mirror for a procedure ID they have seen, and update/delete are then pinned to them (firestore.rules:385-388). The exploitable population is named by the code itself: src/modules/loto/services/procedures.js:565-610 exists because approved procedures that predate the mirror have a printed code and no mirror, resolving to 'does not match a current procedure'. Confirmed on the emulator: bob (orgB) created /procedureQr/P1 = {orgId:'orgB', title:'SAFE TO WORK'}; alice (orgA) was then denied create (L384), update (L385) and delete (L388). docs/SECURITY.md:151-181 (S-07/S-08) closed the post-state trap on UPDATE for /qr, /permitQr and the LOTO field-tenanted collections; the create-side ID-namespace claim was not in scope and is still open.
</details>

### MEDIUM-7 / 39 — closed, with a correction worth reading

The triage row above originally said "no withdrawal logic found". **That was
wrong, and it was wrong the same way the audit itself is wrong elsewhere: I
grepped for `delete|close|expire` near `permitQr` and concluded from an absence.**
The logic existed the whole time, in `src/modules/ptw/lib/publicPermit.js`,
under names my search could not have matched.

What was already true before this session:

- The crew is published as **counts**, not names — `participantCount`,
  `fireWatcherCount`, `hasConfinedWatcher`. The register's "participants with
  employer, fire watchers" exposure had already been closed.
- `issuedToName` is retained **deliberately**, with the reasoning written down:
  challenging a job means asking whether the person in front of you is the one
  it was issued to, and the paper permit at the barrier carries that name anyway.
- A permit reaching Closed has every describing field actively blanked on the
  write that closes it, rather than left behind by a status-only merge.

So the finding as written was about 90% stale. What was genuinely left is
narrower and was **not** visible from the register's description:

**The withdrawal had no time bound, and it only ever happened on a write.**

`TERMINAL_STATUSES` excludes `NOT_CLOSED` (expired) on purpose — an expired
permit that was never closed is exactly the one somebody should still be able to
read and challenge. Sound, and the test pinned it. But it is an argument with a
clock in it and it was written without one, so an expired permit published its
job, location, hazards and issued-to name **indefinitely**. Worse, withdrawal
runs inside `mirrorDisplayFields`, which only executes when something writes the
mirror — and nothing ever writes an abandoned permit again.

**The behaviour therefore selected for neglect**: close a permit properly and it
went quiet; forget it entirely and it published forever.

Fixed in two halves, because either alone leaves the hole:

1. `isStale()` in `publicPermit.js` — after `STALE_AFTER_DAYS` (7) past the
   *effective* end date, extensions included, the write path withdraws even
   though the status is not terminal. The challenge window is preserved intact.
2. `withdrawStalePermitMirrors`, a nightly sweep in `functions/index.js`, which
   is the half that reaches permits nobody will ever write again.

Both resolve every ambiguity toward keeping the detail: a permit with no
readable end date is never withdrawn, and an extension delays withdrawal without
its approval state being consulted. Removing information from a safety page is
the direction that can hurt somebody.

Covered by `functions/lib/permitMirror.test.js` (21) and the new block in
`publicPermit.test.js`.

## MEDIUM (40)

### MEDIUM-1 · A.5.18 Access rights · `app`

**Revoking a user does not revoke their outstanding ID token, leaving up to an hour of live Cloud Storage access after suspension**

**Gap.** Firestore denies immediately, because every rule re-reads the profile through `myProfile()` (firestore.rules:30-43). Cloud Storage does not: storage.rules reads the claim off the presented token (storage.rules:48), and the suspended user's cached ID token still carries the old orgId until it expires — up to one hour. Combined with the finding above, that is a one-hour window in which a just-offboarded person can still read and delete their former employer's files. AuthContext.jsx:156 forces a fresh token on sign-in, which helps the newly-approved case but does nothing for the revoked one.

**Fix.** In syncUserClaims (functions/index.js:82-92), when `next.orgId` is null and `existing.orgId` was not, call `await getAuth().revokeRefreshTokens(uid)` after setCustomUserClaims. That forces the client to re-authenticate and makes revocation effective in seconds rather than up to an hour.

<details><summary>Evidence</summary>

Suspension is the only revocation path: src/pages/admin/Users.jsx:47 calls setUserStatus(uid,'suspended'), which writes the profile (src/shared/org/orgData.js:210-218). That fires syncUserClaims (functions/index.js:62-94), and claims.js:35-39 correctly returns `{orgId:null, role:null}` for a non-approved profile, so the claim is cleared at functions/index.js:85. Nothing anywhere calls `getAuth().revokeRefreshTokens(uid)` — grep across functions/ and src/ returns no match. `setCustomUserClaims` does not invalidate tokens already issued.
</details>

### MEDIUM-2 · A.8.3 Information access restriction · `app`

**Files are handed out as permanent unauthenticated download URLs that no rule ever sees**

**Gap.** Every access decision in storage.rules and every revocation in the finding above is bypassed by possession of the URL. Three consequences follow. A departing or suspended member keeps whatever URLs they copied, permanently. A URL forwarded outside the tenant works for anyone. And the site-scoped document restriction — which firestore.rules:241-244 goes to considerable trouble to make list-safe — only restricts the metadata document; the bytes behind the URL are reachable by anyone holding it, including an org member whose access does not reach that site if the URL leaks by any other route.

**Fix.** Stop persisting getDownloadURL output. Store only the storage `path` (already returned by putFile) and resolve bytes at render time through `getBlob(ref(storage, path))`, which is rule-checked, or mint short-lived signed URLs from an authenticated Cloud Function. If the current URLs stay, at minimum add a documented rotation step (overwrite `downloadTokens` metadata) to the offboarding process.

<details><summary>Evidence</summary>

src/shared/storage/adapters/firebase.js:41 `const url = await loaded.mod.getDownloadURL(ref)`, returned as `{url}` and persisted onto the record by putFile (src/shared/storage/index.js:147). getDownloadURL mints a `?alt=media&token=<uuid>` URL that Firebase serves without authentication and without evaluating storage.rules. Nothing in the repo rotates or revokes that token — grep for getDownloadURL/updateMetadata across src/ shows the one call site and no rotation path.
</details>

### MEDIUM-3 · A.8.5 Secure authentication · `app`

**MFA is fully built but optional for everyone, including admins, and no rule ever asks for it**

**Gap.** The account with the most authority in a tenant — an admin who can promote roles, rewrite anyone's site access, delete the organization and read every module — is defensible with a password alone, and that password can be six characters (see the next finding). The build half of MFA is done and done well; the enforcement half does not exist.

**Fix.** Two layers. In firestore.rules, add `request.auth.token.firebase.sign_in_second_factor != null` as a conjunct of `isAdminOf()` once admins are enrolled, so admin-only writes require a second factor unbypassably. In the console, turn on the Identity Platform MFA requirement. Sequence the rule change after enrolment or you lock the admins out — mfa.js:10-17 already makes exactly this point.

<details><summary>Evidence</summary>

src/shared/auth/mfa.js implements TOTP enrolment and the sign-in challenge correctly, and AuthContext.jsx:168-178 and :186-202 route both the password and SSO paths through the challenge so an MFA-enabled account cannot lock itself out. src/pages/auth/Security.jsx:212-222 offers enrolment as self-service, with prose recommending it to admins — a recommendation, not a requirement. Nothing enforces it: firestore.rules never references `request.auth.token.firebase.sign_in_second_factor`, ProtectedRoute.jsx:15-33 checks only auth/profile/approval/role, and there is no per-org 'require MFA' setting in OrgSettings. docs/SECURITY.md:38-43 (S-05) already records 'admin accounts have no MFA' as an open console item.
</details>

### MEDIUM-4 · A.5.17 Authentication information · `app`

**Password policy is six characters, checked only in React, and the two code paths disagree**

**Gap.** A six-character password with no complexity requirement, no breached-password check and no reuse restriction is the floor for every self-registered account, including the admin created at org registration (src/shared/org/orgData.js:89-98). The org founder — the most privileged identity in a tenant — passes through RegisterOrg.jsx, the weaker of the two paths. The inconsistency with ForcePasswordChange also means the app states two different minimums to two different users.

**Fix.** Raise both signup paths to a single shared validator (12+ characters, or a zxcvbn-style strength floor) and put the same rule behind ForcePasswordChange so there is one answer. Then configure the Identity Platform password policy in the console so the bar is enforced server-side where the client check cannot be skipped — the client check is a courtesy, the console policy is the control.

<details><summary>Evidence</summary>

src/pages/auth/Signup.jsx:31 `if (form.password.length < 6)` with the hint at :87; src/pages/auth/RegisterOrg.jsx:21 the same at :61. Both are client-side toasts before `createUserWithEmailAndPassword` — the Firebase REST signUp endpoint is reachable directly and enforces only Firebase's own six-character default, so the check adds nothing an attacker cannot skip. src/pages/auth/ForcePasswordChange.jsx:30 requires eight for a provisioned employee's replacement password. No Identity Platform password policy is configured anywhere in the repo (firebase.json, .env.production).
</details>

### MEDIUM-5 · A.5.17 Authentication information · `app`

**The forced temporary-password change is a React route guard the user can clear themselves**

**Gap.** The temporary password is now strong and unique per account (provisioning.js:30-38), which removes the guessing attack the old shared constant allowed — that fix is real and it is the reason this is not high. What remains is credential lifecycle: nothing expires the temporary password, nothing forces its rotation, and the flag that claims to force it can be switched off by the person it constrains. A credential handed over verbally or by email stays valid indefinitely.

**Fix.** Add `mustChangePassword` to the pinned-field list on the self-update branch of firestore.rules:517-521, so only an admin may clear it, and have ForcePasswordChange set it through a callable that verifies the password actually changed. Alternatively give provisioned profiles a `tempPasswordExpiresAt` and deny `isApprovedMemberOf` past it, which makes the expiry unbypassable.

<details><summary>Evidence</summary>

Provisioned accounts are written `status:'approved'` (src/shared/auth/provisioning.js:73) and `mustChangePassword:true` (provisioning.js:78) — fully live from the moment of creation. The only enforcement is src/shared/auth/ProtectedRoute.jsx:25 `if (profile.mustChangePassword) return <ForcePasswordChange />`. firestore.rules:517-521 pins only `role`, `status`, `siteId` and `access` on a self-update, so `mustChangePassword` is a field the account holder may write: `updateDoc(userRef(uid), {mustChangePassword:false})` from the browser console clears the gate without touching the password. Nor is the app the only client — the account is usable through the Firestore and Storage SDKs directly, which never load ProtectedRoute.
</details>

### MEDIUM-6 · A.5.18 Access rights · `org`

**No periodic review or recertification of standing role and site-access grants**

**Gap.** A.5.18 requires access rights to be reviewed at planned intervals. That is a process with a named owner and a cadence; it cannot be satisfied by code alone. The repo neither performs it nor produces the artefact a reviewer would need.

**Fix.** ORG: define the cadence and owner (per-org admin, quarterly is typical for a safety system with contractor auditors). APP support that would make it feasible: stamp `accessGrantedAt`/`accessGrantedBy` on setUserAccess and add a Users filter for grants older than the cadence — a small change, but the control itself remains a process.

<details><summary>Evidence</summary>

Grants are written and audited but never revisited: src/shared/org/orgData.js:340-352 (setUserAccess), :369-380 (grantAccessRequest) and :220-228 (setUserRole) each log an entry and stop there. Nothing in the profile carries an expiry, a review date or a grantor attestation — see the field set written at src/shared/auth/provisioning.js:67-81 and src/shared/org/orgData.js:123-137. src/pages/admin/Users.jsx surfaces pending approvals and pending access requests (:101-102) but has no view of grants that have gone stale.
</details>

### MEDIUM-7 · A.8.12 Data leakage prevention · `app`

**The public permit mirror publishes worker names and employers, and is never withdrawn when the permit closes or expires**

**Gap.** Personal data is disclosed to an unauthenticated audience for the operational lifetime of a permit and then forever after it. Anyone who photographed the QR during the job keeps indefinite access to who was on the crew and who they work for. Compare the LOTO mirror, which solved the identical problem correctly by publishing 'whether, not who' (src/modules/loto/utils/publicProcedure.js:38-52).

**Fix.** Give the mirror the same discipline as the LOTO one plus a lifecycle: drop participants/fireWatchers/confinedWatcher/createdByName from fullMirror, or replace them with counts; and on closure/expiry either delete the mirror or overwrite it with a terminal 'this permit is closed' stub. Both are single-writer changes in src/modules/ptw/lib/firestore.js.

<details><summary>Evidence</summary>

src/modules/ptw/lib/firestore.js:127-156 (fullMirror) writes to the world-readable /permitQr: issuedToName, createdByName, jobLocation, jobDescription, fireWatchers, confinedWatcher, and participants mapped to {name, type, company}. firestore.rules:400-403 acknowledges the content ('the issuer's and holder's names, fire watchers and the full participant list with each worker's employer'). The mirror is deleted only when the PERMIT is deleted (src/modules/ptw/lib/firestore.js:475); closure and expiry only refresh status fields via mirrorStatusFields (src/modules/ptw/lib/firestore.js:159-166), which carries no deletion or redaction. The token is the sole control and it is printed on a sheet of paper taped up in a work area.
</details>

### MEDIUM-8 · A.8.12 Data leakage prevention · `app`

**The document classification field that enforces site-level confidentiality is writable by any ordinary member**

**Gap.** The label is enforced on read and unprotected on write, so any member who can reach a restricted document — legitimately, via their own site access — can publish it org-wide, and any member who learns a document ID can overwrite a restricted document they cannot read. A classification control that the classified party can remove is advisory.

**Fix.** Add a conjunct to the documents write path requiring the four classification fields to be unchanged unless isElevatedOf(orgId): `col != 'documents' || isElevatedOf(orgId) || (request.resource.data.visibility == resource.data.visibility && request.resource.data.siteId == resource.data.siteId && …)`. Extend tests/documents.rules.test.js, which currently lists and gets but does not attempt the relabel.

<details><summary>Evidence</summary>

firestore.rules:763-765 restricts reads on /organizations/{orgId}/documents by `visibility`, `siteId`, `siteRegion`, `siteEntity` (canReadDocument/reachesSite, firestore.rules:220-244). **Gap.** These are img src, not href, so a javascript: or data:text/html value does not execute — this is not script execution. The residual risk is that a stored http(s) URL in an evidence field causes the viewer's browser to fetch an attacker-controlled endpoint when a report is opened or printed, leaking IP and timing, and that the pattern is inconsistent enough that the next reviewer cannot tell raw-by-decision from raw-by-oversight.

**Fix.** Wrap the three bindings in safeSrc, and hold the line mechanically: add a custom ESLint rule (or eslint-plugin-react's no-danger plus a no-restricted-syntax selector on JSXAttribute[name.name=/^(href|src)$/] whose value is not a safeHref/safeSrc call) so a future raw binding fails CI rather than review.

<details><summary>Evidence</summary>

safeHref/safeSrc are applied at ~30 sinks across the app (e.g. src/modules/ptw/pages/PermitDetail.jsx:393 and :410, src/modules/training/pages/MyLearning.jsx:31 and :84, src/modules/emergency/pages/SiteDetail.jsx:264-390, src/modules/loto/components/procedures/ProcedureView.jsx:142-144). Three bind a stored value raw: src/modules/incidents/components/IncidentReportDoc.jsx:140 (`<img src={img}` where img is photos[].dataUrl), src/modules/fire/components/MockDrillReport.jsx:195 (`<img src={src}` from r.photos[]), and src/modules/fire/pages/MockDrills.jsx:663 (`<img src={enlarge}`, set from p.dataUrl at :572/:636 — the same value is passed through safeSrc for the thumbnail and raw for the enlargement). eslint.config.js:44-49 configures no rule that would catch a raw href/src, so adherence is by review only.
</details>

### LOW-27 · A.8.26 Application security requirements · `app`

**Storage rules allow any content type, so a member can host arbitrary HTML/SVG on the project's storage origin**

**Gap.** Any approved member of any tenant can upload text/html or image/svg+xml and obtain a durable Firebase download URL that serves it with that type. Because storage is on firebasestorage.googleapis.com rather than the app origin, this cannot reach a signed-in session's Firestore authority — the impact is phishing content hosted under the project's storage domain and script execution confined to that origin.

**Fix.** Add a content-type allow-list to the create rule in storage.rules:62-64, e.g. `&& request.resource.contentType.matches('image/(png|jpeg|webp|gif)|application/pdf')`, and add a matching case to tests/storage.rules.test.js alongside the existing size test at :118. Note SVG should be excluded rather than allowed as an image type.

<details><summary>Evidence</summary>

storage.rules:51-69 — the create rule constrains tenancy (inOrg), overwrite (resource == null) and size (< 20 MB) but never request.resource.contentType. The `accept` attributes on the upload inputs are the only type filter and are client-side hints: src/modules/ptw/pages/PermitDetail.jsx:379 (application/pdf,image/*), src/modules/incidents/components/FileUploader.jsx:76, src/modules/emergency/pages/SiteDetail.jsx:252, src/modules/training/pages/Courses.jsx:236. src/shared/storage/index.js:137-154 (putFile) passes the blob to the adapter with no type assertion; it sanitises the filename (:80-87) and the path segments (:97-109), but not the content type. tests/storage.rules.test.js:118-127 tests the size cap and :129 the overwrite denial; no test asserts a content-type restriction.
</details>

### LOW-28 · A.5.21 Managing information security in the ICT supply chain · `app`

**GitHub Actions dependencies are pinned to mutable tags in a job that holds the production service-account key**

**Gap.** A `v4` tag is a moving reference the supplier controls; if it is re-pointed — by the maintainer or by an account compromise — arbitrary code executes inside the deploy job with the Firebase service-account JSON on the filesystem and full deploy rights to weehs-4eb28. ### LOW-29 · A.5.20 Addressing information security within supplier agreements · `app`

**Production deploys authenticate with a long-lived service-account key interpolated into the shell and left on disk**

**Gap.** A static service-account JSON is a credential with no expiry, no per-run scoping and no rotation trigger — the strongest key in the system, held indefinitely in a GitHub secret. Interpolating it into the script body (rather than passing it through `env:` as the earlier step does) writes the secret into the runner's generated shell script on disk in addition to the target file, and a value containing a single quote would break the command in a way that could echo fragments into the log.

**Fix.** Move to Google Cloud Workload Identity Federation with `google-github-actions/auth` so the job mints a short-lived token and no static key exists. If the static key must stay for now, pass it via `env:` and reference `"$SA"` inside the script, grant the account only Firebase Hosting Admin + Firebase Rules Admin rather than Editor, and set a rotation date.

<details><summary>Evidence</summary>

.github/workflows/deploy.yml:86-90 writes the key with `echo '${{ secrets.FIREBASE_SERVICE_ACCOUNT }}' > "$GOOGLE_APPLICATION_CREDENTIALS"`, expanding the secret directly into the shell script body, and reuses the file at deploy.yml:94-98 without ever removing it. The setup instructions at deploy.yml:5-8 direct the operator to generate a static private key from the Firebase console. Note the contrast with deploy.yml:30-33, where the same secret is correctly passed via `env: SA:` rather than interpolated.
</details>

### LOW-32 · A.8.32 Change management · `app`

**A release that deploys nothing reports success**

**Gap.** The reasoning is sound for forks, but the consequence in the production repo is that a tag push which deployed nothing is indistinguishable in the Actions UI from one that shipped a release — a green check against `v1.2.0` may mean the release is live or may mean a secret was rotated and not replaced. **Fix.** Keep the skip for `pull_request`/fork contexts, but make the tag trigger fail loudly when credentials are absent — a release that cannot deploy is a failed release. Alternatively name the skip in the job summary rather than only as a notice.
